## 首轮 77.5% → 92.5% 之间修了什么

首轮跑出 77.5%，逐条核对后发现**三类问题责任不同**：

| 问题 | 责任方 | 处理 |
|---|---|---|
| 模型用 `scale` / `multiplier` 当参数名 | **提示词缺陷** | 系统提示词补上每个动作的**精确参数名与范围** |
| `checkpoint.activate` / `platform.visibility.set` 被拒绝 | **编译器缺陷** | 模型没见过关卡，编译器按关卡能力补合法默认 id |
| `timer.interval` 从不触发 | **运行时缺陷** | 实现定时事件（≥500ms，按整周期推进防漂移） |
| 未知参数被静默忽略（要 100 倍得到 1.2 倍） | **校验缺陷** | 未知参数直接拒绝，不再静默丢弃 |
| "多个动作应生成多条规则" | **我的测试期望错误** | 规范允许 1 条规则 2 个动作，下限改为 ceil(动作数/2) |

最后一行要特别说明：**其中 4 条失败是我自己的评测标准写错了**，不是产品问题。如果不逐条核对而直接"修产品"，会改坏本来正确的东西。

## 剩余 3 条失败

| ID | Prompt | 结果 | 判断 |
|---|---|---|---|
| c07 | 捡到金币玩家加速 5 秒，跳跃高度 1.3 倍 | unsupported | 两个效果分属不同触发语义，模型选择拒绝 |
| c11 | 关卡开始激活检查点，并生成金币 | unsupported | 关卡开始"激活检查点"语义上无意义 |
| k04 | 重力反转后，敌人减速 5 秒 | unsupported | "重力反转后"不是已注册的触发事件 |

这三条**不是解析失败，是模型主动拒绝**。前两条可以争论为合理的保守行为（需求本身有歧义）；
k04 是真的漏了——它应当映射到 `player.jumpCommitted`（重力反转的因）。

**我没有为了凑分修改语料。** 失败照实记录。

## P95 延迟未达标

28.6 秒 vs 目标 15 秒。原因有两个：

1. 组合类 Prompt 的输出较长，偶发 `finish_reason=length` 截断后触发有界重试，整整翻倍一次耗时
2. 网络抖动

中位数 3.9 秒是正常的。要压 P95 需要：把 `max_tokens` 再放宽（已从 2048 提到 3072）、
或对截断改为"不重试、直接报错并要求玩家简化"。后者更快但用户体验更差，
**这个取舍需要产品决策，我没有单方面改。**

## 置信度限制

50 条样本，92.5% 的 95% 置信区间约为 **[84%, 97%]**（Wilson 区间）。
也就是说：真实能力很可能在 84–97% 之间，**不能宣称"稳定 92.5%"**。
要收窄到 ±3% 需要约 300 条样本。

## 下一步建议

1. **扩语料到 300 条**才能给出可信的能力区间
2. k04 这类"因果表述"（X 之后 ⇒ 用 X 的触发事件）需要提示词里显式举例
3. P95 需要产品决策：要速度还是要完整

## 复现

评测是可复现的：语料版本 `1.0.0`，报告含 `corpusVersion` / `provider` / `model`
与每条用例的 `latencyMs`。换模型重跑只需改 `--provider`。
